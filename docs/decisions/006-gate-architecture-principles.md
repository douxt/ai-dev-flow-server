# ADR-006: 测试门禁体系设计原则

## 状态：已采纳
## 日期：2026-07-30

## 背景

UMES3 项目连续三次出现"测试全绿 → 手工验证失败"：

| 次数 | 日期 | 被穿透的门禁 | 补充的门禁 |
|:--:|------|------|------|
| 1 | 07-28 | 无 C0（当时无静默跳过检查） | C0.2 恒真断言 |
| 2 | 07-30 | C0-C6 全部通过 | C7 Action 走 UI |
| 3 | 07-30 | C0-C7 全部通过 | G0（本次提案） |

**模式**：每次出问题 → 追加一条门禁 → 下次从不同角度穿透。门禁靠"伤疤"增长，永远在防守上一场战争。按此模式，C8、C9、C10 会无限追加，但永远有下一种漏洞。

根源：**现有 C0-C7 全部检查"测试长得像测试吗"（形式正确性），无一条检查"测试能拦住 Bug 吗"（有效性）。**

## 决策

测试门禁体系遵循三条设计原则：

### 原则 1：两条轴线

```
形式正确性（"测试写得对不对"）      有效性（"测试能不能拦 Bug"）
  C0 语法反模式                        G0 反向突变测试
  C1 全部 RED
  C2 RED 原因正确
  C3 RED commit 格式
  C4 无实现混入
  C5 AC 覆盖数量
  C7 Action 走 UI
  R7 分层一致性
  S13 E2E 比例约束
```

两条轴线互补，缺一不可。新门禁必须明确归入其中一条轴线，不接受"都有点"的模糊定位。

### 原则 2：防御问题类别，不是防御单个实例

| 坏的门禁（防实例） | 好的门禁（防类别） |
|------|------|
| "不能 apiCall 绕 UI" | "Action 路径必须真实" → C7 |
| "不能用 toBeGreaterThanOrEqual(0)" | "断言必须可证伪" → G0 |
| "不能硬编码 sale_id=40462" | "测试数据必须可重置" → 数据工厂 |
| "if (count() > 0) 包裹 expect" | "断言不可静默跳过" → T7 |

G0 的特殊价值：它不查具体模式（apiCall / count>0 / 弱断言），而是**通用的有效性验证**——一条门禁覆盖多种漏洞类型。

### 原则 3：通用防线优先于特化规则

新增门禁前先问：**现有通用防线（G0）能拦住吗？** 能 → 不加特化规则。不能 → 先尝试扩展通用防线，再考虑特化。

```
新漏洞发现
  → G0 能拦？→ 是 → 记录为 G0 用例，不加新门禁
  → 否 → 能否扩展 G0？→ 是 → 扩展
  → 否 → 新增门禁（明确归入形式/有效性轴线）
```

## 后果

- 门禁清单不会无限增长——新漏洞优先归入 G0 用例，只在 G0 覆盖不到时新增门禁
- 每个门禁在清单中有明确的"轴线"标签，方便审查新增门禁是否重复
- 原则 2 要求所有未来门禁以类别描述（"Action 路径必须真实"），不以具体反模式命名（"禁止 apiCall"）
- 定期审查：当一条轴线上累积超过 7 条门禁时，触发架构审查——是否有更通用的门禁可以合并它们

## 拒绝的方案

- **每个漏洞直接加一条 C8/C9/C10**：违背原则 3，导致门禁清单无限增长，维护成本递增
- **只保留 G0，删除 C0-C7**：G0 是有效性补丁，不能替代形式检查。形式检查发现问题快（秒级 grep），G0 慢（5 分钟/条），两者互补
- **全量 Mutation Testing 工具化**：StrykerJS 不支持 Playwright E2E（[GitHub issue #5286](https://github.com/stryker-mutator/stryker-js/issues/5286)），对纯 E2E 项目无自动化工具可用
