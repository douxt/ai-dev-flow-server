## 一、为什么还要做阶段二

阶段一修好了巡检本身，但今天暴露的真正问题是**运维可观测性缺口**，不是单个 bug：

| 事实 | 持续时长 | 谁发现的 |
|---|---|---|
| `health-check.sh` 自愈逻辑完全失效（`set -e` 吞掉计数 + 路径失效） | **30+ 天** | 我上机取证的偶然发现 |
| QQ 账号掉线、Bot 停止工作 | **约 2 天**（2026-09-09 16:18 → 09-11 10:52 人工扫码） | 探针实测时的偶然发现 |
| 仓库与 NAS 在版脚本完全不同（3410B vs 1486B） | 未知（≥1 个月） | 同上 |

三件事的共同点：**没有任何机制把它们告诉人**。阶段一只补上了"巡检能看见自己"（心跳行 + 失败计数），异常**仍然只写在 NAS 本地日志里**，等人主动去看。阶段二就是补这一层。

## 二、目标与边界

**目标**：异常能自己找到人；静默失效能被周期性发现；运维流程可复用而非重新摸索。

**不做**：告警平台化、NAS 侧新增常驻守护进程、容器级巡检（NAS 上另有 12 个容器：immich×3、n8n、emby、moviepilot、xiaoya、sun-panel、code-server——属新工程，等本套机制跑稳再评估）、升级 NapCat/LangBot 版本。

## 五、执行顺序与门禁

```
T0 ✅ ─→ T2 ─→ T1 ─┬─→ T3
                   └─→ T5
T4 / T6 / T7 / T8（可与主线并行，各自独立）
```

**每个工单必须满足的门禁（沿用阶段一纪律）**

1. worktree 开发（`nas-observability`），一工单至少一个 commit，不攒批
2. 可本地验证的先写零依赖自测（`tests/integration/*selftest*.sh`），再上机
3. 动 NAS 前：备份 → 影子运行（改路径参数指向 `/tmp`）→ 实测 → 才落生产
4. 部署后：两端 md5 一致 + `bash nas/check-drift.sh` 通过
5. 长操作不在 SSH 链路里等（用 `nohup … &` 或后台等待，不前台 `sleep`）
6. 每次记录：改了什么、证据是什么、怎么回退

## 六、观察窗与复盘标准

阶段二全部落地后观察 **24 小时**，看四个数（都从巡检与看门狗产物里取）：

| 指标 | 期望 |
|---|---|
| 心跳行数量 | ≈ 288 行/天（每 5 分钟一行），无缺口 |
| `FAIL #` 出现次数 | 0（无真实故障）或与真实故障一一对应 |
| `ACCOUNT-OFFLINE` | 0；若 >0 → 说明 QQ 又掉线，且开发机应在 1 小时内收到通知 |
| 看门狗告警次数 | 0（静默原则）；>0 必须是真问题，否则调阈值 |

复盘问题：告警是否及时且不吵？有没有"应该报但没报"或"报了但没意义"的情形？

### T6 调查完成（2026-09-11，待选 A/B）

漂移成因查明：反向 WS 与账号用**环境变量**配置（compose `WS_URLS`/`ACCOUNT`），而 OneBot HTTP 服务走 JSON；JSON 里 `"url": "0.0.0.0:5700"` 在当前 NapCat 4.18.1 下**不生效**，实际落到容器内 `127.0.0.1:3000`（登录后才监听）。宿主 `:5700` 有 docker-proxy 但无后端（`Connection reset`）；宿主 `:3000` 是 nginx（另一服务）。

推荐 **方案 B**（统一到实际，不改配置）：零调用方依赖 5700，改配置风险非零（napcat 配置改动可能触发掉线，而掉线需人工扫码）。
