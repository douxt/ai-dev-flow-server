# DSH on NAS 教训（2026-09-11）

> 把 DeepSeek Harness 装进 NAS 的 code-server 容器、并做到"重建不丢"过程中的可迁移教训。
> 架构决策见 [ADR-012](../docs/decisions/012-dsh-inside-code-server-container.md)，运维流程见 [docs/bot/dsh-on-nas.md](../docs/bot/dsh-on-nas.md)。

## 一、先摸清"目标环境缺什么"，再选安装方式

这次的方案形态**完全由实测约束决定**，而不是由设计偏好决定。事前我做了三条廉价探针（NAS 上有没有 node、容器里有什么工具、目标端口是否空闲），
直接改掉了原本的独立容器方案。

**可迁移做法**：动手前先跑一份"环境能力清单"——运行时版本、包管理器、缺的二进制、内核特性、网络可达性。
其中**运行时版本要实测到"能启动"而不是"能安装"**：`npm install -g` 成功 ≠ 能跑（本次 DSH 在 Node 20 上装得好好的，一启动就因 `node:module`/`node:zlib` 缺新 API 而插件树加载失败）。

## 二、"能访问"要分层验证，否则会得到假成功

远程服务的可用性有四层，每层都能单独失败：**端口发布 → 反向代理 → 应用侧 Host/Origin 校验 → 前端实际连通**。

本次的坑：DSH 的 `/api` 要求 Host 是 loopback 或在 `trustedHosts` 内。若不声明 `--trusted-host`，**页面会正常打开**（静态资源不校验），但对话永远连不上。
如果只测"首页 200"就宣布完成，会交付一个看起来能用、实际不能用的东西。

**可迁移做法**：
1. 探针必须打到**真实业务端点**，不能只打首页
2. 反向代理链路要单独确认**它是否改写了 Host 头**（本次实测 `tailscale serve` 保留原 Host，方法：带 `Origin` 打 `/api`，用 403/404 区分"被拦"与"已进路由"）
3. 验证要从**真实对端**发起。本次 NAS 连自己的 tailnet 名/IP 全部超时（既有现象），只有从另一台 tailnet 设备测才拿到有效结论
4. 准备一个**必须被拒绝**的对照用例（`Origin: https://evil.example.com` → 403），否则无法区分"栅栏在工作"和"根本没栅栏"

## 三、往持久目录里放东西，先问"进程会不会 watch 它"

`DSH_HOME` 会被 DSH 递归 watch。我在里面留了一个 **root 所有、权限 600 的备份文件**，
结果新起的 DSH 进程 chokidar `EACCES` 直接崩掉。

**可迁移做法**：
- 备份、临时文件、日志一律放在被 watch 目录**之外**
- 用过的自检：`find <dir> ! -user <uid> -o ! -group <gid>` 与 `find <dir> ! -perm -u+r`
- 手工以 root 创建的种子文件，**必须 chown 给运行用户**再交给服务

## 四、隔离机制不可用时，要么修好它、要么显式放弃并写下来

NAS 内核 5.10 **既无 Landlock 又未开 user namespaces**（`unshare --user` → `EINVAL`），
DSH 的 `workspace-write` 沙箱"没有可用后端"，于是 bash 工具 **fail-closed 拒绝执行**；换 bubblewrap 也不通（它需要 user namespaces）。

**可迁移做法**：
1. 先试厂商指出的替代路径（报错里就写了"Install bubblewrap or run a Landlock-enforcing kernel"）——试了再放弃，结论才有分量
2. 找不到可用的隔离后端时，把边界上移到**容器本身**，并把这个取舍写进 ADR（含 blast radius），不要默默降级
3. 优先用厂商留的正门（本次是 `DSH_PERMISSION_MODE` 环境变量），而不是绕过它的 CLI 校验。**绕过被明确拒绝的开关，会在下次升级时以更贵的方式失败**

## 五、"重建不丢"是一条分层规则，不是一次配置

能推导出规则的问句是：**这一项在镜像里还是在卷里？**

- 程序（运行时 + CLI + 包管理器）→ 镜像，钉精确版本
- 状态（凭据、设置、插件、会话）→ 卷，且**必须是已挂载的卷**（默认路径 `~/.dsh` 恰好没挂）
- 包缓存 → 顺带确认落在哪（本次 pnpm store 恰好在同卷，等于白赚）

**验证方式**：真实 `build` + 重建容器，然后比对**重建前后指纹**（文件 md5、插件清单 md5、文件数、凭据 size/mode、扩展数、登录返回码、进程清单）。
指纹比对比"看着没问题"可靠得多——本次 12 项全绿才敢说"不丢"。

## 六、顺手的账要当场算

回灌仓库时发现：`docker/code-server/*` 的仓库镜像**落后 NAS 一个多月的改动**（离线安装、openkb、`/data` 权限等都没入库）。
如果直接基于仓库版本改，会把这些改动一起抹掉。

**可迁移做法**：改任何"NAS 上是事实源"的文件前，先 `scp` 回来 diff 一次，确认仓库是否落后；
回灌时把**历史差异与本次改动分开说明**（本次 diff 里两者混在一起，已在计划文档里标注）。
