# DSH 0.1.0-rc.7 → 0.1.5-rc.2 升级教训（2026-09-13）

> NAS code-server 容器内 DSH 升级实操。流程见 `docs/bot/dsh-on-nas.md` §五，事实变更见 ADR-012「修订」。
> 本篇只写**可迁移**的部分。

## 一、升级前先问"上游有没有动我们依赖的行为"，而不是"有没有新功能"

这次两处都撞到：

- `dsh-persona` 的 `config.text` 改名 `prefix` —— 直接让我们自建 preset 挂载失败；
- web 新增 `BrowserAuth` —— **推翻了 ADR-012 D5 的前提**（"DSH 自身不提供认证"），入口用法整体变了。

**可迁移做法**：读 release notes 时，「其他变更 / 破坏性变更」段优先级高于功能列表；
再对自家配置目录做一次"字段级 grep 预检"（`grep -rn "text:" <preset 目录>`）。这次预检在升级前就发现了必炸点。

## 二、两版 schema 互斥时，操作顺序只有一个正确答案

旧版只认 `text`(string)、新版只认 `prefix`(string) ⇒ **不存在"提前改好再升级"的两全解**。
只能选一个窗口期：先重建升级 → 立刻改那一行。反过来做的话，升级前服务就已经先挂了。

**可迁移做法**：遇到"改配置能兼容新版但会弄坏旧版"，把两个版本的 schema 各自读一遍再定顺序，
并**明确写下窗口期谁承担**（本次：升级期间 NAS GUI 会话不可用约 1 分钟）。

## 三、验收基线要用"改动时间窗 + 差分"，不要拿两天前的指纹表

计划文档里那张 12 项指纹表是 09-11 的。升级后一对：凭据 54→223B、文件 870→976、插件 2→5 条——
全是两天内**正常使用长出来的**，不是升级丢的。照旧基线判会得出"状态被破坏"的错误结论。

**可迁移做法**：`find <目录> -newermt '<动作时刻>'` + `diff 备份 在版` 才是"这次动了我该动的没有"的正确问句。

## 四、"记录过的坑"不等于"不会踩"——我这次自己又踩了一遍

手册 §三 的警示明写"备份一律放 `DSH_HOME` 之外"，我第一步就做成了 root 在 `DSH_HOME` 里 `cp` 出 `.bak`。
发现后立刻挪出并 `find ! -user 1000` 自检归零。

**可迁移做法**：把这类约束**下沉到脚本/命令模板**里（手册里那条 sed 命令应自带"备份到 DSH_HOME 外"的路径），
而不是指望下次还记得读它。

## 五、判"回归 or 上游行为变更"，最便宜的办法是找一台同版本的对照机

升级后首页 200→401、WS 101→502，看起来像大事故。开发机同为 rc.2，一条 curl 就拿到**逐字相同的 401 文案**，
立刻定性为"新版本预期行为"，省掉一整轮排障。

**可迁移做法**：跨版本/跨端异常，先做**同版本对照**，再查配置与网络。

## 六、同一次改动在"NAS 侧"和"仓库侧"要用同一套语义，别各用一种手法

我用 `sed 's|@deepseek-ai/dsh@0.1.0-rc.7|…|'` 改 NAS 的 Dockerfile，只命中了 `RUN` 行；
上一行的**注释**写的是 `（0.1.0-rc.7）`（不含包名）没被命中。仓库副本我是整段替换、注释一起改了
⇒ 两边就差一行注释，`check-drift.sh` 报 DRIFT。**而且这条 DRIFT 在我提交前就存在**，差点被当成"历史遗留"放过去。

**可迁移做法**：

- 改"事实源 + 仓库镜像"两侧时，**别一边 sed、一边整段替换**；两侧用同一种编辑语义，或改完立刻 `diff` 一次。
- 注释也算漂移。对账是逐字节的就得分字节对齐，别觉得"只是注释"就豁免。
- 看到既有 DRIFT 先问"是不是我刚弄出来的"再归因。本次靠 `check-drift` 当场兜住，
  修正注释即归零（注释不产生 layer，**不需要为此重建镜像**）。

## 七、别把"一次观察"升级成"机制结论"写进文档——我这次就写错了一条

我看到"重启后 token 变了"，就在手册里写成"**重启后 cookie 失效，要重新取 URL**"。
这是把**相关性当因果**：token 变的是"一次性登录凭证"，与已签发的 cookie 是两码事。

被问"必须带 token 吗"时才去读实现：`isAuthenticated` 只校验**持久签名密钥**（`initializeSecret`
落盘在 `$DSH_HOME/.credentials.yaml`，属卷内状态）+ authority + 有效期，**根本不查 launchToken**；
再实测——重启前拿到的 cookie，重启后仍 `200`。结论反过来了：**token 每台设备只用一次，cookie 30 天有效、
且不随重启/重建失效**（`cookieMaxAgeDays` 默认 30）。

**可迁移做法**：
- 写运维文档里的"行为断言"前，先读实现或做一次**针对性实验**；没做之前就标"未验证/推测"。
- 判据要选对：`token 变了` 不能推出 `cookie 失效`，得看**校验路径到底读哪份状态**。
- 状态落在哪一层（镜像 / 卷 / 进程内存）决定了它扛不扛重启——这与"重建不丢"是同一套问句。

## 八、命令层小坑（当天各踩一次）

- `docker exec` **不带 `-i`** 时，`ssh host 'docker exec ... bash -lc "cat > /tmp/x"' <<'EOS'` 这种"用 heredoc 往容器里塞脚本"会**静默生成空文件**，后续执行无任何输出——看着像命令没跑。
- 外层 heredoc 里再套 heredoc 喂 stdin 极易错乱；跨 ssh+docker 传脚本，要么 `docker exec -i`，要么先 `scp` 再执行。
- `| tail -N` 缓冲到进程结束才落盘：长构建的日志文件中途是 0 字节，别误判成"没在跑"（改看 `docker images` 时间戳）。
