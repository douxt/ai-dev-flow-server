# NAS 可观测性重建教训（2026-09-11）

背景：巡检脚本静默失效 30+ 天、QQ 掉线 2 天、仓库与线上脚本完全脱节——三件事都没有任何机制告诉人。
本篇只记**可迁移的教训**；事实与流程分别归档在 `nas/README.md`、`nas/INVENTORY.md`、`skills/nas-ops/`、ADR-011。

## 一、"静默失效"是最贵的故障类型（四型）

| 型 | 实例 | 识别信号 |
|---|---|---|
| 逻辑不可达 | `set -e` + 会失败的外部命令 → 后续计数/重启分支永不可执行（30 天自愈从未生效） | 状态文件（计数/锁）从不产生；日志里没有"FAIL/OK"这类本该出现的行 |
| 引用失效 | 脚本引用的路径过了重构（`tests/` → `tests/scripts/`） | 每轮一条同样的报错，被 `\|\| true` 吞掉 |
| 版本脱节 | 线上 3410B / 仓库 1486B，md5 不同 → "照仓库修"修的不是线上那份 | 仓库改完线上无变化；md5 对不上 |
| 判据错位 | 探针查 `localhost:3000/get_status`，而该 API **登录后才监听** | 探针永远失败 → 误重启；或永远成功 → 假健康 |

**纪律**：① 任何 `|| true` 包住的步骤，失败必须留日志行；② 会失败的探针命令用 `cmd || rc=$?` 捕获，别让 `set -e` 接管；③ 线上在版文件必须回灌仓库 + md5 对账；④ "看起来在跑"（cron 触发、日志在涨）≠"在起作用"。

## 二、健康检查/探针设计三原则

1. **不要用真实业务链路当健康检查**：旧探针发真消息走 `/sync` 全链路（含 LLM）→ 288 次/天 LLM 开销、写入聊天归档表、抢 WS 队列，而且 **LLM 抖动会被误判为服务故障 → 自动重启容器**。探针只证"活着"；业务验证用低频金丝雀（每 6h 一次，成本降 98%）。
2. **故障分三类，动作不同**：可自愈（进程死/端口不通 → 重启）｜需人工（账号掉线/风控 → 只告警，**重启无效**）｜需告警但别动（LLM/检索抖动 → 只告警，连续 N 次才报）。把三类混成一个"失败计数"必然误重启。
3. **单点判据不够，要跨层交叉**：`link`（OneBot WS 连着）**不等于**已登录——掉线 24 小时期间 WS 一直是通的（0 条 WS 错误）。必须叠加**状态探针**（登录态 API/文件新鲜度）+ **日志事件扫描**（离线/二维码/身份失效），二者互补：事件覆盖"瞬间"，状态覆盖"持续"。

**上机验证是硬要求**：+ 探针 ⑤ 就是在真机上才发现 `Errno 99`、端口事实与配置不符（配置写 `0.0.0.0:5700`，实际只在容器内 `127.0.0.1:3000` 且登录后才监听；宿主 `:3000` 是 nginx）。**不要相信配置文件，要看实际监听与响应。**

## 三、观测体系的分层与"执行者放哪"

1. **检测放 24/7 的机器，发送放有通道的地方**。本次犯错：把看门狗放开发机（"那里有权威仓库"），而开发机常关机 → 24/7 覆盖形同虚设。**先问"这台机器 24/7 吗"，再问"它有什么"**。
2. **不要把主机数当冗余**：云服务器发 Telegram 走的是**同一个网关 Clash 代理**，所以"NAS → 云 → Telegram"没有任何冗余，只是多一跳。引入新主机前先确认它是否与现有路径共用出海口。
3. **告警用文件队列做接口**：生产者只写 `state/alert`（零网络依赖、绝不因网络阻塞业务）；消费者（NAS `alert-flush`，*/2）**原子认领**（`mv` → `.sending`）→ 逐条发送 → 成功归档 `alert.history`，失败**回队重试**（不丢数据）。
4. **死者开关**：每日固定时间摘要。收不到摘要本身就是信号——这是"没有第二个观察者"时唯一能暴露整机/通道故障的手段。
5. 通道先验证再谈体系：`getMe` 只读校验、发一条测试消息，别等真出事才发现发不出去。

## 四、会重复踩的工具/环境坑（今天各踩了 1–2 次）

| 坑 | 表现 | 正确做法 |
|---|---|---|
| `ssh -n` 吞 stdin | 管道传数据（凭据/消息）到远端变成空值 | 需要 stdin 时用 `ssh -T`，不要 `-n` |
| heredoc 里 tab 被吞 | TSV 字段粘连成一列，解析全空 | 用 `\|` 等可见分隔符，或 `printf` 写文件 |
| `git show main:path` 失败时 | 空输入 md5 = `d41d8cd9…`，伪装成"文件漂移" | 先 `git cat-file -e main:path` 判断存在性 |
| 前台 `sleep` 等 cron 窗口 | 慢（一个 5 分钟周期要等 10+ 分钟）且长调用会被工具超时杀掉 | 后台 job + 结果落文件，不阻塞对话 |
| 沙箱边界 | 不能写 `~/`、`/var/spool/cron`（crontab）、`/home/dou/wt`（`wt` worktree 根） | 仓库内 `.worktrees/` 建 worktree；cron 一行交给人工装 |
| 改生产文件前不演练 | 一旦写错直接影响线上 | 先备份 → **影子运行**（把状态目录/日志指到 `/tmp`）→ 再落生产 → 事后 md5 |
| 重启窗口内的瞬时错误 | langbot 重启时 napcat 报 1 条 `ECONNREFUSED`（15s 重连自愈） | 判据是"**序列完成后**是否仍 refused"，不是"窗口内一条都没有" |
| 验证"漂移检出" | 真改生产文件去测有风险 | 用**影子清单**（正确文件 + 故意错的 md5）验证同一代码路径 |

## 五、决策与协作偏好（用户明确表达）

- **NAS 自洽优先**：不要为了发通知把第三方主机牵扯进来；能在一台 24/7 机器上闭环就闭环。
- **风控型掉线不做自动重登**：`ACCOUNT + NAPCAT_QUICK_PASSWORD` 能自动重登，但凭据落盘风险 > 收益（风控场景密码登录同样可能被拦）→ 保持"告警 + 人工扫码"。
- 先给方案再执行；但当**事实推翻前提**时（云不可达/代理可用/机器常关机）应立即改并**把修正写进文档**，不要沿用错误叙事。
