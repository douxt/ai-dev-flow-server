# 测试分层策略

> DevFlow 测试层级选择指南 — AI 在 `/to-spec` 阶段按决策树选择正确测试层级
> 配套门禁：spec-checklist S13（must-pass E2E ≤ 15%）+ test-checklist R7（/tdd 分层一致性）

## 集成测试统一定义

```
集成测试 = 两个及以上真实模块协作，外部依赖 stub 或真实。
  ├─ API 集成：HTTP 请求验证端到端 API 契约（Playwright request context / curl 探针）
  ├─ 组件集成：React/Vue 组件组合行为（Vitest + Testing Library）
  └─ 模块集成：public API 协作（函数调用 + mock 外部依赖）
```

## 测试类型选择规则（必须遵守）

```
## 测试类型决策树

0. 本次变更含业务逻辑？
   → 否 → 跳过测试，标注 [no-test]（配置/文档/依赖升级/样式微调）
   → 是 → 继续

1. 这是新功能还是 bug 修复？
   → bug 修复：
     用户报告 UI 缺陷 → E2E 回归（保底 1 条，不增新 E2E）
     API 返回错误数据 → API 探针回归
     计算/逻辑错误 → 单元回归
     数据库一致性 → 存储层回归
   → 新功能/hotfix → 继续

2. 验证的是 UI 交互行为还是数据/逻辑行为？
   → UI 交互（点击/拖拽/动画/布局/弹窗）：
     是否跨系统流程（支付网关/外部 API/第三方服务/OAuth 登录）？
       → 是 → E2E（仅端到端流程验证，不覆盖 UI 细节）
       → 否 → 能否拆为独立交互步骤？→ 集成测试
   → 数据/逻辑行为 → 继续

3. 涉及多模块/服务通信？
   → 是 → 集成测试
     技术栈速查：
       Node → Vitest + Testing Library 或 Playwright request context
       PHP → 裸 PHP assert() + shell runner 或 docker compose exec 探针
       Go → go test + httptest
       Python → pytest + responses
       Rust → cargo test + mockall

4. 纯逻辑/计算/状态迁移？
   → 是 → 单元测试
     技术栈速查：
       Node → Vitest（项目已有则直接用）
       PHP → 裸 assert()（php -d assert.active=1）
       Go → go test（内置）
       Python → pytest
       Rust → #[test]

5. 代码不可隔离测试（无 DI/全局变量/Smarty 混用）？
   → 先输出"提取纯函数/加 seam"修复建议 → 降级为集成测试

[hotfix] 紧急修复
   → 绕过决策树，直接 E2E 快速验证
   → /to-tickets 时自动拆出事后补测 issue（测试类型按决策树正常分配）
   → S13 门禁自动豁免

## 防冗余检查（每条必须过）

- 此行为已被更低层测试覆盖？→ 降级
- 已有特征测试（tests/characterization/）覆盖该接缝？→ /tdd 测试降级到更低层
- 能用集成替代 E2E？→ 降级
- 能用单元替代集成？→ 降级
- 检查命令：grep 功能名 tests/ 下是否已有测试

## 默认规则

- 禁止非跨系统流程写 E2E
- 选 E2E 必须注明决策路径理由（"判断2→跨系统流程: <具体系统>"）
- [hotfix] ticket 直接 E2E + 事后补测试跟踪 issue
```

## 各层反模式

| 层 | 反模式 | 正确做法 |
|----|--------|---------|
| E2E | 每个 CRUD 操作一条 E2E | 仅端到端流程（跨系统/支付/OAuth），细节下沉到集成 |
| E2E | Action 走 `apiCall()` 绕 UI | Action 必须 `page.click`/`page.fill`（Setup/Teardown 例外） |
| 集成 | Mock 了被测模块本身 | 只 mock 外部边界（网络/文件/DB），被测模块用真实实现 |
| 集成 | 测了实现细节（内部函数调用顺序） | 测输入→输出契约，不测内部调用链 |
| 单元 | 测了框架代码（路由/ORM 映射） | 框架行为由框架自己测，只测你写的逻辑 |
| 单元 | 每个文件一个测试文件 | 按行为组织，不按文件 1:1 映射 |
| 通用 | 无业务逻辑的纯配置/常量文件写测试 | 标注 [no-test]，不浪费 |

## 遗留项目起步

### Node 项目（已有 Vitest）

```bash
# 已有 Vitest → 直接用，不装新框架
npm test  # 确认现有 98 条能跑

# 加第一个 API 集成测试
# tests/integration/api_store.spec.ts
import { test, expect } from 'vitest'
// nock v13 锁定版本（兼容 Node 14）
import nock from 'nock'

test('GET /api/paint/list 返回涂料列表', async () => {
  const res = await fetch('http://localhost:8080/api/paint/list?sale_id=40462')
  expect(res.status).toBe(200)
  const data = await res.json()
  expect(data.code).toBe(0)
  expect(Array.isArray(data.list)).toBe(true)
})
```

### PHP 项目（无测试框架）

```bash
# 零依赖起步：裸 PHP assert
php -d assert.active=1 tests/integration/test_store_api.php

# 或 docker compose 隔离执行
docker compose run --rm php php -d assert.active=1 /app/tests/integration/test_store_api.php
```

### 渐进策略

1. 新 ticket 走决策树 → 自然产生集成/单元测试
2. 存量 E2E 不碰（Strangler Fig：新功能新方式，旧功能不改测试方式）
3. E2E 比例靠增量稀释 → 新测试下沉，E2E 占比自然下降
4. 不设"把 E2E 重写为集成"的硬性迁移目标
