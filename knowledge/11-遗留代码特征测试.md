# 遗留代码特征测试

> 原则：Cover and Modify — 先建安全网，再走钢丝。
> 触发：`/characterize` | ticket 含 `[legacy]` 标签 | 改动文件无测试覆盖
> 工具：`skills/characterize/` | `gate-checklists/characterization-checklist.md`

## 一、核心概念

**特征测试（Characterization Tests）** — Michael Feathers《Working Effectively with Legacy Code》——
捕获代码"当前实际行为"的测试。不测对不对，只测改了之后不变。

```
标准 TDD:  写期望行为 → RED → GREEN → REFACTOR  （测"应该怎样"）
特征测试:  跑当前代码 → 记录实际输出 → 锁定为基线  （测"现在怎样"）
```

| | Edit and Pray | Cover and Modify |
|--|-------------|-----------------|
| 做法 | 分析代码 → 最小改动 → 祈祷没坏 | 写特征测试锁行为 → 改动 → 测试确认 |
| 风险 | 高 | 低（有安全网） |

## 二、五阶段生命周期

### 1. 创建（/characterize）

- ANALYZE：理解代码公共接口、接缝、依赖、副作用
- CAPTURE：写特征测试，记录当前实际输出
- 铁律：**特征测试必须立即 GREEN**。不 GREEN = 理解错了，修测试不修代码

### 2. 验证（元验证）

确认安全网真的在起作用：
1. 临时修改被测代码一行（如改返回值）
2. 跑特征测试 → **必须变 RED**
3. 恢复修改 → **必须恢复 GREEN**

不通过 = 特征测试有问题，修复后重新验证。

### 3. 执行（锁行为后改动）

特征测试 GREEN → 安全改代码 → 每次改动后跑特征测试确认无意外回归。

### 4. 调和（Reconcile）

特征测试失败时，判断原因：
- **有意行为变更**（bug 修复/功能修改）→ 审查 diff → 更新快照 → 记录原因
- **意外回归** → 修复代码，不改测试

### 5. 退役

当新的 TDD 测试覆盖了同一代码路径后，特征测试可以删除。
退役条件：对应功能有 ≥1 个正式 TDD 测试 + 测试 GREEN + 人工确认。

## 三、接缝识别

Seam = 不改源码就能改变行为的点。

| 代码类型 | 推荐接缝 | 特征测试方式 |
|---------|---------|------------|
| HTTP API 端点 | URL 路径 | HTTP 探针 + JSON 快照 |
| 纯函数/工具函数 | 函数签名 | 参数-返回值录制 |
| DB 写入操作 | 函数前后 DB 状态 | SELECT 对比 |
| 多层调用链 | 最外层公共接口 | 全输出录制（胖测试） |
| React 组件 | 组件 props | 渲染快照 + page.route() mock |
| 第三方 SDK 封装 | 封装函数签名 | I/O 录制 |

## 四、基础设施故障豁免

特征测试 RED 时，先区分原因：

| 错误类型 | 信号 | 处理 |
|---------|------|------|
| 基础设施故障 | connect refused / timeout / 502/503 | 标记 `[infra]`，修复环境，不归因理解错误 |
| 理解错误 | 返回值/行为与预期不符 | 修测试，不修代码 |
| 代码变更（有意） | 调和阶段已知变更 | 更新快照 + 记录 |

**环境探针**：特征测试前先跑一步轻量健康检查（curl API health / SELECT 1），不通则先修环境。

## 五、文件组织

```
tests/characterization/
├── ticket-001-paint_list_test.php      # 特征测试，命名含 ticket ID
├── ticket-002-order_calc_test.php
├── ticket-003-paint_create_test.js
└── snapshots/                           # 快照文件
    ├── ticket-001-paint_list.json
    └── ticket-003-paint_create.json
```

- 特征测试文件命名：`<ticket-id>-<feature>_test.*`
- 快照文件命名：`<ticket-id>-<feature>.json`
- 多 ticket 操作同一文件时，各 ticket 独立命名，互不覆盖

1. ticket Scope 中涉及的文件在 `tests/` 下是否有匹配的测试文件
2. 无匹配 → 提示用户"建议先 /characterize 锁行为"

用户输入 `/characterize` → 按 SKILL.md 三步执行。

spec-checklist S12：若涉及零测试覆盖模块，spec 中标注特征测试需求，/to-tickets 据此拆出前置 `[legacy]` ticket。

## 七、技术栈速查

| 栈 | 快照方案 | 工具 | 详细文档 |
|----|---------|------|---------|
| PHP | HTTP 探针 → JSON 快照 + DB 状态对比 | PHPUnit / 裸探针 | `stacks/php/legacy-characterization.md` |
| Node/React | 组件渲染快照 + E2E page.route() | Vitest `toMatchSnapshot()` | `stacks/node/legacy-characterization.md` |
| Python | API 响应快照 + Approval mode | pytest-syrupy | `stacks/python/legacy-characterization.md` |
| Go | 输出 golden file | `testdata/` + 表格测试 | `stacks/go/legacy-characterization.md` |
| DB 密集 | SELECT 结果集对比 + dump diff | 框架无关 | 见各栈模块 |

## 八、反模式

| ❌ | ✅ |
|----|----|
| 特征测试写 `assertTrue(true)` 绕过 | 必须与实际输出交互的断言 |
| "顺手修一下"特征测试捕获的 bug | 先锁行为，改动时再修 |
| 特征测试和 TDD 测试混在同一文件 | `tests/characterization/` 独立目录 |
| 特征测试永久保留不清 | TDD 测试覆盖后退役 |
| 基础设施挂了还归因"理解错误" | 先探针，再归因 |
